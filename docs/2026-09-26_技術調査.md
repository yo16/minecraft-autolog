# 技術調査: Minecraft の操作ログを自動で撮れるか(2026-09-26)

## 0. 結論(先に)

| やりたいこと | できるか | 方法 | 備考 |
|---|---|---|---|
| ラッパーから Minecraft のウィンドウを認識する | **できる(実機確認済み)** | Win32 `EnumWindows` でタイトル `Minecraft…` かつプロセス `javaw.exe` を探す | 9/26 実機: `exe=javaw.exe class=SDL_app client=854x480` |
| F2 を外部から送ってスクショを撮らせる | **できる(前面のときだけ)** | `SendInput`。`PostMessage` は不可 | 9/26 実機: `SendInput --focus` 成功、`PostMessage` はスキャンコード有無とも無反応。26.3 は入力層が GLFW → **SDL3** |
| F2 を「常に送り続ける」 | できるが **推奨しない** | — | 毎回チャットに「保存しました」が出て流れる、PNG が溜まる、前面にないと届かない。F2 は「ここぞ」の手動マーカーとして残す方がよい |
| ラッパー側で画面を連続キャプチャする | **できる(実機確認済み)** | Windows Graphics Capture(WGC)を Python の `windows-capture` から使う | 9/26 実機: 黄色い枠なし、別窓を重ねても撮れる、1 枚 20〜80KB、FPS 低下なし。最小化中だけ撮れない |
| コメント前後の「動画」を残す | できる(複数手段) | ①WGC の静止画リングバッファ ②Xbox Game Bar「直前 30 秒を録画」③AMD Instant Replay ④OBS リプレイバッファ | ②③はこの PC に入っていて追加インストール不要。ただしホットキー起動のみ |
| 音声でコメントを入れる(typeless) | できるが **採用しない** | typeless は Minecraft のチャット欄への挿入まで実機で成功 | 「前面アプリのカーソル位置に挿入する」方式なので、Minecraft を操作したまま・チャットを開かずには使えない(§5) |
| **話すだけでコメントを残す**(Minecraft のフォーカスを奪わない) | **できる(この PC で実測済み)** | ラッパーがマイクを直接録り、ローカルの faster-whisper で文字起こし(`poc/voice_note.py`)。区切りは Minecraft 未使用のキー(右 Ctrl など)か声の有無 | large-v3-turbo が CPU で実時間の 0.5〜1.4 倍。裏で処理するので体感待ちなし(§5) |
| コメントに時刻を付けて画像と対応づける | **できる(実機確認済み)** | `latest.log` に F2 保存・チャット・進捗・一時停止が秒単位の時刻付きで出る。音声メモは録音開始時刻を持つ | 9/26 実機で F2・チャット・Esc の行を確認 |
| 一時停止(Esc)の時間をプレイ時間から除く | **できる** | 統計ファイル `players/stats/<uuid>.json` の `play_time`(一時停止を除く)と `total_world_time`(含む)。Esc のたびに書き直される | 9/20〜26 の実データで play_time 3h08m / total 6h56m(§6) |

**推奨する最小構成**: 「ラッパーが WGC で数秒おきに WebP を撮り続ける」+「コメントはラッパー自身がマイクを録って faster-whisper で文字起こし(右 Ctrl で区切る。Minecraft は前面のまま)」+「ラッパーが `latest.log` と統計ファイルを監視して、コメント・F2・進捗の時刻に前後の画像を紐づけ、`events.jsonl` と画像を書き出す」+「minecraft-log 側はそれを読んで `log.md` を組み立てる」。詳細は §7。

## 2. Minecraft ウィンドウの認識

普通の Win32 API で足りる。

- `EnumWindows` → 可視かつタイトルが `^Minecraft\*?\s`(Mod 導入時は `Minecraft*`)に一致するものを列挙
- `GetWindowThreadProcessId` → `QueryFullProcessImageNameW` で実行ファイル名を取り、`javaw.exe` / `java.exe` に絞る(ランチャーは `Minecraft.exe`、タイトル `Minecraft Launcher` なので除外できる)
- 複数あればクライアント面積が最大のもの

`poc/probe_window.py` に実装済み。9/26 の実機で次が取れ、窓クラスは `SDL_app` で確定した。

```
hwnd=0xaf0b34 pid=14876 exe=javaw.exe class=SDL_app client=854x480 title='Minecraft 26.3 - シングルプレイ'
```

## 3. F2 を外部から送る

### 3.1 手段

| 手段 | 仕組み | 条件 | 評価 |
|---|---|---|---|
| `SendInput`(仮想キー F2、スキャンコード 0x3C) | OS のキュー経由で「本物のキー」として前面窓へ | **Minecraft が前面**であること。他アプリが前面だとそちらに F2 が飛ぶ | プレイ中は前面なので実用上はこれで十分。最も確実 |
| `PostMessage(hwnd, WM_KEYDOWN/WM_KEYUP, VK_F2, lParam)` | 窓プロシージャに直接投げる | 前面でなくても届く可能性がある | SDL3 の実装上は受け付ける(下記)。ただしフォーカスのない窓に届いたイベントを Minecraft 側が無視する可能性があり要実機確認 |

### 3.2 SDL3(Windows)がどう扱うか — ソース確認

`src/video/windows/SDL_windowsevents.c` の `WM_KEYDOWN` 処理:

- スキャンコードは `lParam` の 16〜23 bit から取る。**0 なら `MapVirtualKey(vk)` で補完**し `virtual_key = true` にする
- イベントを流す条件は `virtual_key || !raw_keyboard_enabled || text_input_active`。つまり **スキャンコード 0 で投げれば、RAW キーボード入力が有効でも必ず流れる**
- `GetKeyState` などで実キー状態を照合して捨てる処理はない

→ `PostMessage` はスキャンコードを付けずに投げるのが安全(`poc/send_f2.py` の既定)。一方、SDL はキーイベントに「キーボードフォーカスのある窓 ID」を付けるため、Minecraft が非フォーカスだと窓 ID が 0 になり、Minecraft 側が無視する可能性がある。

**9/26 実機結果**: `SendInput --focus` は成功、`PostMessage` はスキャンコードの有無にかかわらず何も起きなかった。上の「窓 ID が 0 で無視される」推定どおりと見てよい。つまり **F2 を外から送るには Minecraft が前面にある必要がある**。ただし §4 のとおりキャプチャはラッパー側で行うので、最終的な設計では F2 の送信は使わない。

### 3.3 「常に F2 を送り続ける」を勧めない理由

1. **チャットが流れる**: 1 枚ごとに `スクリーンショットを….pngとして保存しました` がチャットに出る(9/20 のログで確認)。5 秒おきなら常に画面左下がこの通知で埋まる
2. **ファイルが溜まる**: 854×480 でも PNG 1 枚 0.4 MB。5 秒おきで約 300 MB/時、1080p にしたら 1.5 GB/時
3. **前面依存**: ブラウザで攻略を見ている間は撮れない(あるいは別アプリに F2 が飛ぶ)
4. **`latest.log` が汚れる**: 1 枚ごとに 1 行増え、あとで「本人が意図して撮った F2」と区別できなくなる

代わりに、F2 は今までどおり「ここは残したい」の手動マーカーとして使う。時刻はファイル名にもログにも入るので、ラッパー側の連続キャプチャと突き合わせるだけでよい。

## 4. ラッパー側で画面を撮り続ける

### 4.1 手段の比較

| 手段 | 種類 | 窓単位 | 隠れていても | 導入 | 制御 | 評価 |
|---|---|---|---|---|---|---|
| **Windows Graphics Capture**(`windows-capture` 2.0.1、Rust 製 Python 拡張) | 静止画/フレーム | ○ | ○(最小化は×) | `pip` のみ(Python 3.9+ abi3、3.13 で動作確認) | 完全にプログラム制御 | **本命**。この PC で実測: 初回フレーム 0.17 秒、正しい画像。フレームは「画面が変化したとき」だけ届くので静止中はほぼ無負荷 |
| ffmpeg `ddagrab` + `h264_amf` | 動画(画面全体) | ×(座標で切り抜き) | ○ | 導入済み | コマンド | 連続録画したいなら現実的。GPU エンコードで CPU をほぼ使わない |
| ffmpeg `gdigrab title=…` | 動画/静止画 | ○ | △ | 導入済み | コマンド | ハードウェア描画の窓で黒画面・静止画になる報告が多い。避ける |
| Xbox Game Bar「直前 N 秒を録画」(Win+Alt+G) | 動画 | ゲーム窓 | ○ | 導入済み、設定でバックグラウンド録画をオンにする | **ホットキーのみ**(ラッパーから `SendInput` で押すことは可能) | 15 秒〜10 分の巻き戻し録画が無料で手に入る。MP4 は `ビデオ\キャプチャ` へ |
| AMD Software Instant Replay(Ctrl+Shift+S) | 動画 | 画面/ゲーム | ○ | 導入済み | ホットキーのみ | Game Bar と同等。どちらか片方でよい |
| OBS Studio + obs-websocket | 動画/静止画 | ○(Game Capture は OpenGL フック) | ○ | `winget install OBSProject.OBSStudio` | WebSocket で `SaveReplayBuffer` / `SaveSourceScreenshot` | 最も高機能だが常駐が重い。動画品質にこだわる段階になったら |
| Fabric Mod を自作 | ゲーム内 | — | — | Fabric は 26.3 対応済み | 何でもできる | バニラ最新版を追う運用と相性が悪い(リリース直後は Mod が追いつかない)。今回は見送り |

### 4.2 WGC の実測(2026-09-26。エクスプローラーの窓と Minecraft 実機)

- `WindowsCapture(window_hwnd=…, cursor_capture=False, draw_border=False)` → 0.17 秒で最初のフレーム、正しい画像
- **9/26 Minecraft 実機**(`poc/capture_loop.py`): 黄色い枠は出ない、別ウィンドウを上に重ねても撮れ続ける、1 枚 20〜80KB、FPS の低下なし
- 静止した窓では 5 秒間に 1 フレームしか届かない = 変化があるときだけ来る。Minecraft は常に描画が変わるので、数秒おきに間引いて保存すればよい
- キャプチャ画像はタイトルバーを含む「DWM の拡張フレーム」範囲。`DwmGetWindowAttribute(DWMWA_EXTENDED_FRAME_BOUNDS)` と `ClientToScreen` の差でクライアント領域だけ切り抜ける(`poc/capture_loop.py` に実装。エクスプローラーの窓で 1012×671 のクライアント領域が切り出せた)
- Windows 11 では捕捉中の窓に黄色い枠が出ることがある。`draw_border=False` を指定しているが効くかは実機で確認。効かなければ「設定 > システム > ディスプレイ > グラフィック > 画面キャプチャの境界線」で消せる(24H2 以降)

### 4.3 容量の見積もり(実測ベース)

| 形式 | 1 枚(854×480) | 5 秒おき・1 時間 | 20 時間(1 シーズン) |
|---|---|---|---|
| PNG(F2 と同じ) | 約 430 KB(平均)〜740 KB | 約 300〜530 MB | 6〜10 GB |
| JPEG 品質高め(`-q:v 3`) | 約 130 KB | 約 90 MB | 1.9 GB |
| **WebP 品質 80** | **約 64 KB** | **約 46 MB** | **0.9 GB** |

全部保存しても D: なら問題ない量。ただし minecraft-log のリポジトリに入れるのは「コメントや F2 の前後数枚」だけにする(§7)。

## 5. 音声コメントの入力

### 5.1 typeless の実機結果と、採用しない理由

typeless(Windows 版、日本語対応、既定ショートカットは右 Alt)は「前面アプリのカーソル位置にテキストを挿入する」方式で、API やファイル出力はない。9/26 の実機では、Minecraft で T を押してチャット欄を開き、右 Alt で話すと日本語が入って Enter で `latest.log` に残る、というところまで成功した。

しかし要件は「**Minecraft の操作はそのまま、T のチャット欄すら開かず、話すだけで入力したい**」。typeless は前面アプリに文字を入れる仕組みなので、Minecraft が前面のままなら文字は Minecraft に入る(チャットを開いていなければ操作キーとして解釈される)。別窓に入れるには Minecraft から前面を外す必要があり、要件と両立しない。Windows 標準の音声入力(Win+H)や Wispr Flow なども同じ「挿入」方式なので同じ理由で外す。

### 5.2 採用案: ラッパーがマイクを直接録り、ローカルで文字起こしする(`poc/voice_note.py`)

「文字をどこかに打たせる」発想をやめ、ラッパー自身が音声を扱う。

- **仕組み**: マイクを常時開いておき(`sounddevice`)、区切った区間を WAV に保存 → 裏スレッドで faster-whisper(CPU、int8)が文字起こし → `notes.jsonl` に「録音開始時刻・終了時刻・本文・所要秒」を追記
- **フォーカスを奪わない**: 区切りのキーはグローバルフック(`pynput`)で拾う。Minecraft が前面のままでよい。キーは Minecraft にも届くが、未割り当てのキーなら何も起きない(Minecraft のダッシュは左 Ctrl だけなので既定は **右 Ctrl**。マウスのサイドボタン、Scroll Lock、F13 以降なども選べる)
- **区切り方 3 種**: `toggle`(1 回押して話し、もう 1 回押す。既定)/ `hold`(押している間だけ。サイドボタン向き)/ `vad`(キー不要。声が出たら自動で録音、無音 1.2 秒で区切るハンズフリー)。`vad` はスピーカーからのゲーム音を拾う恐れがあるので、まず `toggle` か `hold`、ヘッドホンなら `vad`
- **時刻**: 「話し始め」の時刻(キーを押す 0.6 秒前まで先読みして取りこぼしを防ぐ)。`capture_loop.py` の画像とはこの時刻で突き合わせる
- **音声を残す**: WAV があるので、あとでより良いモデルやクラウド API で起こし直せる(`--transcribe-file`)。文字起こしの質は後から上げられる
- **Minecraft 用語を「覚えさせる」**: `poc/glossary.txt` に 1 行 1 語で書いた用語を Whisper のヒント(`initial_prompt`)として渡し、「誤 => 正」の行は置換ルールとして結果に適用する。実声の「ピリジャー」は、ヒントなしだと turbo・small とも「フィリッジャー」になったが、用語集に「ピリジャー」を足すだけで両モデルとも正しくなった(§5.3)。ヒントに渡せる長さは約 220 トークンなので、用語集は上の行ほど優先し、起動時に何語まで渡せたかを表示する
- **費用・オフライン**: モデルはローカル、語数制限なし、ネット不要

### 5.3 モデルの速度と精度(この PC で実測)

Windows の日本語音声合成で作った 3 本(5.1 秒・10.5 秒・16.1 秒)を、CPU 8 スレッド・int8・ビーム幅 2・Minecraft 用語のヒント付きで文字起こしした。

| モデル(サイズ) | 5.1 秒の音声 | 10.5 秒 | 16.1 秒 | 誤り |
|---|---|---|---|---|
| `small`(0.5GB) | 2.5 秒 | 3.4 秒 | 4.1 秒 | 羊→筆字、毛を刈って→けを買って、二個→にこ |
| `large-v3-turbo`(1.6GB) | 7.0 秒 | 7.6 秒 | 8.1 秒 | 鉄鉱石→鉄鋼石、刈って→買って(同音の漢字違い)。羊・2 個は正解 |

- 合成音声なので実声では変わる。Minecraft 用語(トウヒ、エンチャントテーブル、ブランチマイニング、ネザー)は両モデルとも正しく出た
- **実声(9/26、ユーザー録音 6.9 秒「ピリジャーがウロウロしているので、ちょっと隠れてます」)**: 右 Ctrl のトグル録音・ビープ・WAV 保存とも問題なし。turbo は 6.7 秒で処理し、本文は正確だったが「ピリジャー」だけ「フィリッジャー」になった。用語ヒントの効果を同じ音声で比較した結果は次のとおり

| ヒント | large-v3-turbo | small |
|---|---|---|
| なし | フィリジャー | フィリジャー |
| 従来の用語ヒント(ピリジャーを含まない) | フィリッジャー | フィリジャー |
| **用語ヒントに「ピリジャー」を追加** | **ピリジャー** | **ピリジャー** |
| `hotwords="ピリジャー"`(ヒント文なし) | ピリジャー | フィリジャー |

→ 用語集を `initial_prompt` に渡す方式で運用する。`hotwords` は small で効かなかった
- 短い発話ほど固定コストが効く(turbo は 5 秒の音声に 7 秒)。裏スレッドで処理するので操作は止まらないが、「言ってから画面に出るまで数秒〜10 秒」は覚悟する
- AMD GPU は CTranslate2 が Windows で使えないので CPU 推論。8 スレッドでもゲームがカクつくなら `--threads 4`
- 代替モデル: 日本語特化で速い `kotoba-tech/kotoba-whisper-v2.0-faster`、精度重視なら `large-v3`(遅い)。クラウド(OpenAI `gpt-4o-transcribe`、Google、Azure、AmiVoice)は音声が残っているので後からでも適用できる

## 6. 時刻の突き合わせ — `latest.log` が使える

`latest.log` には秒単位の時刻付きで次が出る(9/20 の実ログを `poc/tail_log.py` で解析)。

| 種別 | 例 | 9/20 の件数 |
|---|---|---|
| F2 保存 | `[16:35:01] … [CHAT] スクリーンショットを2026-09-20_16.35.00.pngとして保存しました` | 59 |
| 進捗達成 | `[16:16:25] … [CHAT] greenbanana17が進捗[石器時代]を達成しました` | 7 |
| 一時停止(Esc メニュー) | `[16:33:45] [Server thread/INFO]: Saving and pausing game...` | 67 |
| ワールド開始 / 終了 | `Starting integrated minecraft server version 26.3` / `Stopping server` / `Stopping!` | 1 / 2 |
| ログイン | `Setting user: greenbanana17` | 1 |
| プレイヤーのチャット | `[CHAT] <名前> 本文`(9/20 はチャットを打っていないので実例なし。実機で要確認) | 0 |
| その他の [CHAT] | `リスポーン地点が設定されました`(ベッドで寝た)、`シード値：[…]` など。死亡メッセージもここに出るはず | 8 |

注意点:

- 行には日付がない。日付はファイルの更新日時や読んだ日で補う(深夜 0 時またぎだけ注意)
- Minecraft は起動時に `latest.log` をリネームして作り直す。**ラッパーが開きっぱなしにするとリネームを妨げる**ので、`poc/tail_log.py` のように「0.5 秒ごとに開いて差分を読んで閉じる」方式にする
- 「一時停止」の時刻が取れるので、その間の画像は捨てる(ポーズメニューの絵しか撮れない)

### 6.1 一時停止の解除時刻と「実プレイ時間」— 統計ファイルで取れる

9/26 の実機で、Esc の一時停止は `Saving and pausing game...` として出るが、**解除した瞬間の行はログに出ない**ことが分かった。代わりに Minecraft 自身の統計ファイルが使える。

- 場所(26.3): `saves/<ワールド>/players/stats/<プレイヤーUUID>.json`(現ワールドは `saves/20260920/players/stats/dcc3a910-….json`)
- `stats.minecraft:custom` に、**`minecraft:play_time` = 一時停止を除いたプレイ時間**と、**`minecraft:total_world_time` = 一時停止を含めてワールドを開いていた時間**が tick(1/20 秒)で入っている
- Esc のたび(「Saving and pausing game...」)・自動保存・ワールド終了時に書き直される。実機でも更新時刻 21:59:05 が `Stopping server` の行と一致した
- 9/20〜9/26 の実データ: `play_time` 225,311 tick = **3 時間 08 分**、`total_world_time` 499,804 tick = **6 時間 56 分**。つまり一時停止・放置が 3 時間 48 分あった。minecraft-log の「約 4 時間 5 分」は最初と最後のスクショの時刻から出した値で、実際にはゲームは 22:03 まで開いていた(9/20 のログの `Stopping!` は 22:02:59)

使い方:

1. **作業時間は `play_time` の差分で出す**のが最も正確。セッション開始時と終了時の値を控えるだけでよく、解除時刻を知る必要がない
2. 解除時刻がほしいときは、保存時刻 T1(値 P1)と次の保存時刻 T2(値 P2)から、解除 ≈ T2 − (P2 − P1) ÷ 20 秒。その区間に停止が 1 回だけならほぼ正確(停止中はサーバーが tick を進めないので、自動保存も走らない)
3. 画像側では、WGC のフレーム差分がほぼゼロの区間を「停止/放置」としてタグ付けできる(補助)

ラッパーはこのファイルの更新を監視して、更新のたびに時刻と 2 つの値を `events.jsonl` に書けばよい。ファイルは JSON で、`latest.log` と同じく「開いて読んで閉じる」で十分。

## 7. 推奨アーキテクチャ(MVP)

```
Minecraft (SDL3 / OpenGL, 854x480)
   │ 画面                                   │ latest.log(F2・チャット・進捗・一時停止)
   ▼                                        ▼
autolog デーモン(Python, 常駐)
   ├─ capture   : WGC で 5 秒おきに WebP 保存(全部残す。約 50 MB/時)
   ├─ logwatch  : latest.log をポーリング → イベント化(時刻・種別・本文)
   ├─ voicenote : マイク常時オープン → 右 Ctrl(またはサイドボタン/声)で区切り
   │              → WAV 保存 + faster-whisper で文字起こし → 開始時刻付きで記録
   ├─ statwatch : players/stats/<uuid>.json の play_time / total_world_time を
   │              更新のたびに記録(実プレイ時間・一時停止の除外)
   └─ writer    : sessions/YYYY-MM-DD/events.jsonl + frames/*.webp + audio/*.wav
                  イベントごとに「前 10 秒・当該・後 10 秒」の画像パスを紐づける
   ▼
minecraft-log 取り込み(現行の「チャットで報告 → Claude が整形して log.md 追記」の入力を置き換える)
   - events.jsonl のコメント + 紐づく画像 + F2 画像 → log.md の 1 エントリ
   - 画像は現行どおり YYYY-MM-DD_HH.MM.SS.拡張子 で images/ にコピー(名前順の取り込みがそのまま使える)
```

段階:

1. **実機検証** — 9/26 に窓の認識・F2・WGC・ログ監視・typeless まで完了(§9)。残りは `poc/voice_note.py` を実際の声で試すこと(`poc/README.md` の 6)
2. **capture + logwatch + statwatch + voicenote を 1 つの常駐プロセスに** — 動画なしの静止画のみで一度セッションを回してみる
3. **minecraft-log 連携** — `events.jsonl` を読んで `log.md` を組み立てる取り込みと、`CLAUDE.md` の運用フロー更新。プレイ時間は `play_time` の差分に置き換える
4. (必要なら)動画 — Game Bar の巻き戻し録画をホットキーで叩く、または WGC フレームを ffmpeg で短い動画にまとめる
5. (必要なら)文字起こしの質 — 実声で誤りが目立てば、モデル変更やクラウド API での起こし直し(WAV は残っている)
